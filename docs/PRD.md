## 0. 范围说明与版本路线调整

原规划文档第四节的路线图为：**V1.0 = 剪辑闭环 + 端侧基础 AI；V1.5 = AI Provider 接口 + MCP Server + SRT**。

经产品决策，V1.0 调整为**"剪辑闭环 + 架构骨架"**：Provider 接口与 MCP Server 在 V1.0 **只交付接口定义与空实现骨架**（不交付可用功能），目的是让架构从第一天就具备可插拔性，避免 V1.5 返工。功能可用性时点仍按 V1.5 计。

## 1. 产品目标与一句话定位

### 1.1 一句话定位

**ClipCut Web 是一个开源的、纯浏览器运行的视频剪辑器：零安装、素材不出本地、AI 能力可插拔。**

### 1.2 产品目标（三个，正交）

| # | 目标 | 衡量指标（MVP 验收） |
|---|---|---|
| G1 | **零安装完成一次完整剪辑** | 用户从打开网页到导出 MP4，全程不下载安装任何软件、不上传任何素材文件 |
| G2 | **素材与工程的本地优先与隐私** | 0 次素材上传请求（可由 DevTools Network 面板验证）；工程数据 100% 存于浏览器 IndexedDB |
| G3 | **AI 与导出能力架构可插拔、不绑厂商** | 切换 AI Provider 只需改配置不改代码；导出编码器可替换；核心模块对具体 AI 厂商零引用 |

**明确非目标（V1.0）**：不追求功能数量对标剪映，只打通"导入 → 剪 → 字幕配乐 → 本地导出"最小完整闭环。

### 1.3 关键技术约束（架构必须满足）

- **C1静态可部署**：产物为纯静态资源，可部署到 GitHub Pages / Vercel /任意静态托管，**无服务端、无数据库**。
- **C2 未来 Electron 套壳**：所有与"浏览器环境"耦合的能力（文件读写、持久化、GPU、编解码）必须抽象为接口（`PlatformBridge`），禁止在业务层直接调用 `window.showOpenFilePicker` / `localStorage` 等全局对象。
- **C3 Provider 不绑定厂商**：AI 能力全部经统一 `AIProvider` 接口；软件本体代码中不允许出现具体厂商 SDK 依赖（端侧 ONNX 除外，它属于"内置开箱 Provider"）。
- **C4 降级可用**：WebCodecs 不可用时导出功能必须仍可用（走 MediaRecorder 兜底），并给出明确提示而非报错。

## 2. 目标用户与使用场景

### 2.1 用户分层

| 层级 | 描述 | 核心诉求 |
|---|---|---|
| **U1 内容创作者** | 短视频/自媒体作者，用剪映快速出片，不懂代码 | 上手快、导出快、够用 |
| **U2 隐私敏感用户** | 不愿把私人视频上传到任何服务器的用户 | 素材不出本地 |
| **U3 开发者/自建者** | 想自托管、接AI 模型、做自动化剪辑工作流的工程师 | 可编程、可扩展、开放格式 |

### 2.2 用户故事（User Stories）

- **US-01** — 作为短视频创作者，我想**直接把手机里的视频和图片拖进浏览器**以便不用先传到任何服务器就能开始剪辑。
- **US-02** — 作为短视频创作者，我想**在多轨时间线上分割、裁剪、排序、加文字和配乐**，以便快速产出一条口播/旅拍 vlog。
- **US-03** — 作为内容创作者，我想**导入现成的 SRT 字幕**以便不用手打字幕。
- **US-04** — 作为内容创作者，我想**点一下就把成片导出成 MP4 下载到本地**以便直接发布。
- **US-05** — 作为隐私敏感用户，我想**确认素材一个字节都没有上传**以便放心处理私人/未公开素材。
- **US-06** — 作为开发者，我想**把 AI 字幕/配音能力接到自己部署的模型上**以便不被任何厂商绑定或收费。
- **US-07** — 作为开发者，我想**通过自然语言让 AI Agent 帮我操作时间线**以便把重复剪辑动作自动化。
- **US-08** — 作为开发者，我想**我的工程文件是纯 JSON、可读可diff、可被脚本生成**以便接入自己的工作流。

**V1.0 覆盖情况**：US-01 ~ US-05 为 P0；US-06、US-08 交付"接口可用 + 示例骨架"；**US-07 交付设计骨架，V1.0 不可实际使用**。

## 3. 功能需求表（FR）

优先级定义：**P0 = MVP 必须交付，缺失则不发布**；**P1 = MVP 应交付，时间不足可砍**；**P2 = 明确延后**。

### 3.1 工程与存储

| ID | P | 模块 | 描述 | 验收标准 |
|---|---|---|---|---|
| FR-001 | P0 | 工程存储 | 定义工程 JSON Schema（见第 4 节），实现`serialize()` / `deserialize()` 纯函数 | ① 同一工程保存→加载→再保存，`JSON.stringify` 结果逐字节一致；② Schema 有 TS 类型定义 + JSON Schema 文件；③ 缺字段的旧版本文件能按`schemaVersion` 走兼容层加载，不抛异常 |
| FR-002 | P0 | 工程存储 | 工程（结构化数据）存IndexedDB；二进制素材以 Blob 单独存，JSON 内以 `blobKey` 引用 | ① 刷新页面后工程与素材完整恢复；② DevTools → Application → IndexedDB 可看到工程与 blob 记录；③ 单工程支持 ≥ 500 MB 素材不撑爆 localStorage（**明确禁止把素材放 localStorage**） |
| FR-003 | P0 | 工程存储 | 新建 / 打开 / 另存工程；侧边栏工程列表显示名称、更新时间、时长、缩略图 | ① 可创建 ≥ 10 个工程并切换；② 删除工程有二次确认；③ 工程列表按 `updatedAt` 倒序 |
| FR-004 | P0 | 工程存储 | 导入/导出 `.json` 工程文件到本地磁盘 | ① 导出得到合法 JSON 文件；② 在另一台机器导入后，**素材被标记为"离线缺失"并可通过重新定位本地文件恢复**（relink）；③ 导入时校验 `schemaVersion`，高版本文件拒绝并提示 |
| FR-005 | P0 | 工程存储 | 自动保存：编辑后 3s 防抖落盘 + 页面 `beforeunload` 强制落盘 | ① 强制刷新后最近 3s 内的编辑不丢；② 自动保存不产生新版本号，只更新 `updatedAt` |

### 3.2 素材导入与管理

| ID | P | 模块 | 描述 | 验收标准 |
|---|---|---|---|---|
| FR-006 | P0 | 素材导入 | 通过① 拖拽到素材面板 ② `showOpenFilePicker`/`<input type=file>` 导入：`mp4 / webm / mov / m4a / mp3 / wav / ogg / jpg / jpeg / png / webp / gif` | ① 单次可多选导入 ≥ 20 个文件；② 不支持格式给出明确 toast 而非静默失败；③ `.mov` 若浏览器无法解码，导入成功但标记"需转码"并在导出时提示（V1.0 不保证能播） |
| FR-007 | P0 | 素材解析 | 解析媒体元数据：`duration / width / height / frameRate / hasAudio / codec / mimeType / size` | ① 用 `HTMLVideoElement` + `WebAudio.decodeAudioData` 提取；② 图片走 `Image` 解码取宽高；③ 元数据解析失败不阻塞导入，该素材 `duration=0` 并在UI 标注"未知时长" |
| FR-008 | P0 | 素材管理 | 素材库面板：网格/列表两种视图，展示缩略图、名称、类型图标、时长、分辨率 | ① 支持按名称搜索（防抖 200ms）、按类型筛选；② 支持重命名（`F2`）、删除（`Delete`，二次确认）；③ 缩略图懒加载（IntersectionObserver），滚动 60fps |
| FR-009 | P0 | 素材管理 | 生成并缓存素材缩略图（视频取第 1s 帧；音频取波形峰值数组） | ① 缩略图以 Blob 存 IndexedDB，二次打开工程不重新生成；② 波形归一化为 0~1 的 `number[]`，默认 400 个采样点 |
| FR-010 | P0 | 素材流转 | 从素材面板拖拽素材到时间线轨道，自动生成 clip | ① 拖到视频轨生成视频 clip，拖到音频轨生成音频 clip；② 拖到视频轨的图片生成"默认 5s 时长"的图片 clip；③ 落点自动吸附到播放头/相邻 clip 边缘 |
| FR-011 | P1 | 素材库 | 内置免费可商用素材库面板（Pixabay Music / Pixabay 音效，Freesound CC0） | ① 通过 API 拉取列表，卡片显示名称+ 作者+ 许可（CC0）+ 来源链接；② 点击"下载"将远程素材**缓存为本地 Blob 存入 IndexedDB**，此后**断网可用**；③ 许可信息随素材存入工程 `asset.license`，导出工程时可查看；④ API Key 缺失时面板降级为"仅本地素材"并给出配置引导 |
| FR-012 | P1 | 素材管理 | 第三方素材库连接器**接口定义**（爱给网/AI 音乐生成等） | ① 定义 `MaterialSourceConnector` 接口；② **本期不要求任何实现（含 `LocalFolderConnector`）—— 范围修正见 [§9.2 D-002](#92-d002--fr-012-localfolderconnector-范围裁定)**；③ 本期不实现真实第三方对接；④ **平台层已具备**目录选择与递归列举能力（`WebPlatformBridge.listFiles()`，递归深度上限 2、降级优雅，**均已实测确认**），但**该方法是 `PlatformBridge` 六个方法中唯一零调用方者**，UI 无目录导入入口，用户当前导入路径为 `readFile()`（多选文件）；将来接线时须同时增加单层文件数量上限（如 2000）并在超限时显式告警，详见 [§9.2](#92-d002--fr-012-localfolderconnector-范围裁定) |

### 3.3 时间线（剪辑核心）

| ID | P | 模块 | 描述 | 验收标准 |
|---|---|---|---|---|
| FR-013 | P0 | 时间线 | 多轨模型：视频轨 / 音频轨 / 文字轨，默认 `2 视频 + 2 音频 + 1 文字`，可增删 | ① 轨道类型固定为三类，**同类轨道上下分层，渲染时视频轨按 `order` 从下往上合成**；② 删除轨道时若含clip 需二次确认；③ 至少支持 12 轨 |
| FR-014 | P0 | 时间线 | 轨道操作：静音（mute）、隐藏（hide，仅视频轨）、锁定（lock）、调整高度 | ① 锁定后 clip 不可拖拽/裁剪/删除，但可选中查看属性；② 隐藏轨不参与预览渲染与导出 |
| FR-015 | P0 | 时间线 | 时间标尺（刻度随缩放自适应：ms / s / min）、播放头可拖拽、可点击跳转 | ① 缩放范围 `0.5px/s ~ 200px/s`；② 滚轮缩放以鼠标位置为锚点；③ 空格键播放/暂停 |
| FR-016 | P0 | 时间线 | clip 拖拽移动：同轨内改变 `startMs`，跨轨改变所属轨道 | ① 拖拽中显示吸附参考线（播放头、其他 clip 首尾，阈值 8px）；② 跨类型轨道拖拽**禁止**（视频 clip 不能拖到音频轨）；③ 操作可撤销 |
| FR-017 | P0 | 时间线 | clip 边缘拖拽裁剪：左边缘改 `inMs`，右边缘改 `outMs` | ① 裁剪不越出素材源范围（`inMs≥0`、`outMs≤asset.durationMs`）；② 最小 clip 时长 100ms；③ 缩放/移动鼠标时显示精确时间码提示 |
| FR-018 | P0 | 时间线 | 分割：在播放头处分割选中 clip（快捷键 `S`），两侧共享同一素材引用、独立 `inMs/outMs` | ① 分割点在 clip 首尾 1 帧内，**或分割后任一侧时长不足 100ms** 时提示不可分割（两级规则完整说明见 [§9.1 D-001](#91-d001--splitclip-最小片段时长策略)）；② 视频 clip 分割后需生成第二段缩略图；③ **分割按钮须在播放头进入首/尾100ms 危险区时置为disabled + tooltip**（可操作提示要求，见 [§9.1](#91-d001--splitclip-最小片段时长策略)） |
| FR-019 | P0 | 时间线 | 删除 clip（`Delete`）、复制粘贴（`Ctrl+C/V`，粘贴到当前选中轨道播放头处）、多选（`Shift+点击`、`Ctrl+A`） | ① 删除有 3s 内撤销提示；② 粘贴保持`in/out/speed/transform` 不变；③ 多选后可批量删除与批量静音 |
| FR-020 | P0 | 时间线 | 基础变速：`0.25x / 0.5x / 1x / 1.5x / 2x / 4x`（支持自定义 0.1x~10x） | ① 变速规则：`sourceDuration = outMs - inMs`，`clipDuration = sourceDuration / speed`；② 改speed 时保持 `inMs` 不变、重算 `durationMs`；③ 音频变速**保持音高**（`preservesPitch=true`）；④ 变速后波形按新速度重绘 |
| FR-021 | P0 | 时间线 | 吸附系统：clip 首尾、播放头、整秒刻度，阈值 8px，可全局开关 | ① 关闭吸附后拖拽完全自由；② 吸附命中时显示高亮参考线 |
| FR-022 | P0 | 时间线 | 缩放/滚动：滚轮 = 纵向滚轨，`Ctrl+滚轮` = 时间轴缩放；空格+拖拽 = 平移 | ① 缩放时播放头时间位置保持不变 |

### 3.4 画面与预览

| FR-027 | P1 | 预览渲染 | 缩略图条：视频 clip 在时间线上显示连续帧缩略图 | ① 按需生成，缓存到 IndexedDB；② 长clip 不阻塞 UI |

### 3.7 导出

| ID | P | 模块 | 描述 | 验收标准 |

### 3.10.1 导入路径校验（新增，见 §9.10 D-004）

> 本小节条目由 QA 第五轮横向排查触发（NEW-BUG-01 ~ 04），**新增于第 9 章决策之后**，编号从 FR-063 起。完整论证见 [§9.10](#910-d004--导入路径校验缺失新增-p0-阻塞项)。

| ID | P | 模块 | 描述 | 验收标准 |
|---|---|---|---|---|
| FR-063 | P0 | 工程存储 | **导入路径必须执行 clip 级派生量重算与校验**：`deserialize` 对每个 `assetId !== null` 的 clip 调用 `fixClipDuration` | ① 导入 `durationMs=999999` 而 `inMs/outMs/speed` 正常的工程后，该 clip 的 `durationMs` 被重算为公式值，工程总时长不膨胀；② 文字 clip（`assetId === null`）时长**保持原值不被重算**；③ `outMs <= inMs`（源区间倒置）**显式拒绝并抛错，不让导入成功**（结构性非法，无法重算修正）；④ `durationMs` 与公式不符时**重算为正确值，不报错、不阻断导入**（派生量，重算即可）；⑤ `durationMs` 在工程文件格式中明确为**派生字段**，`inMs/outMs/speed` 为**权威字段**；⑥ **告警经返回值传递**，`deserialize` 保持纯函数（无 UI 副作用），**仅「用户主动导入外部工程文件」路径展示**，`loadProject` / `deleteProject` 不展示。**完整分类与落地约束见 [§9.10 决策一](#决策一新增-fr-063p0阻塞级)** |
| FR-064 | **P0** | 工程存储 | 导入路径**复用**领域层数值范围约束：把 `NUMERIC_RANGES` 抽为可复用的领域层导出函数，供 `setClipProperty` 与 `deserialize` 共用 | ① `transform.scale/rotation/cornerRadius` 与 `text.lineHeight` 在**导入路径**上同样被钳制到合法范围；② `NUMERIC_RANGES` 被导出为领域层公开函数（如 `clampClipProperty(path, value)`），且 `setClipProperty` 与 `deserialize` **均调用同一函数** —— **可由变异测试验证：移除其中任一处的调用，测试必须失败**；③ 新增数值字段时默认走公共约束函数，无需二次接线；④ **必须与 FR-063 同批交付** —— 仅做 FR-063 会留下"导入路径数值校验只覆盖 1/12 字段"的半成品状态，后人无从判断是有意为之还是遗漏 |
| FR-065 | P1 | 工程存储 | `canvas.width` / `canvas.height` / `track.height` 补 Schema 上限 | ① 超出上限的值在**导入时**即被拒绝或钳制（不只在导出层）；② 预览层不因超大画布产生内存风险 |

### 4.1 关键字段约定（实现必须遵守）

| 约定 | 说明 |
|---|---|
| **时长不变式** | 恒有 `durationMs == (outMs - inMs) / speed`。任何变速/裁剪操作后必须重算，不得产生不一致数据。 |
| **时间单位** | 一律毫秒整数。序列化前统一 `Math.round`。 |
| **时间线总时长** | `meta.durationMs` = max(所有 clip 的 `startMs+durationMs`, 所有 cue 的 `endMs`)。 |
| **素材越界** | 任何 `inMs/outMs` 必须落在 `[0, asset.durationMs]` 内；素材 `playable=false` 时允许 `durationMs=0`，UI 标注并禁止上时间线。 |
| **画布比例变更** | 变更 `canvas.width/height` 时，所有 clip 的 `transform.x/y` 按新旧宽高比换算，`fontSize` 按新画布高度/1080 换算，保证视觉一致。 |
| **字段命名** | 一律 `camelCase`；时间后缀 `Ms`，字节 `sizeBytes`，角度 `rotation`（度）。 |
| **未知字段** | 反序列化时**保留**未知字段并原样写回（forward-compatible，便于社区扩展）。 |
| **JSON Schema** | 提供 `schema/project.schema.json`，CI 中用 ajv 校验 fixture。 |

### 9.0.1 通用设计准则（从具体决策中提炼，适用于后续全部设计与实现）

> 以下准则**不是**某一条需求的附属说明，而是从 D-001 / D-003 / D-004 / FR-018③ 等多次决策中反复出现的共同模式中提炼出来的。**新功能设计与代码评审均应以此为准。**

---

#### 准则一 · 能在入口拦住的，不要留到管线里静默失败

**能在入口拦住的，不要留到管线里静默失败。**

用户点击「开始导出」后等待 16.7 分钟、最终得到一段几乎全黑的视频且全程无提示 —— 这比点击时立刻报错**糟糕得多**。同理，把「片段过短」降级为 UI 告警、而丢帧实际发生在渲染管线，等于让系统**同时警告 + 静默丢失**，用户体验反而更差（至少报错能让人知道发生了什么）。

**推论**：
- **入口拒绝优于事后告警** —— 能提前判定的约束，在入口就拦住（FR-018③ 的分割按钮 disabled 态、FR-063 的 `outMs <= inMs` 抛错）
- **告警不能替代拦截** —— 告警只在 UI 层生效，管线层的静默失败它拦不住
- **但可自动修正的数值偏差应静默处理** —— 见准则二

**已由本准则约束的决策**：D-001（100ms 入口拒绝）、D-003（fps 下线前置拦截）、FR-018③（按钮禁用 + tooltip）、FR-063⑤（`outMs<=inMs` 抛错）。

---

#### 准则二 · 区分「结构性非法」与「可自动修正的偏差」

判断依据是**「该错误能否由系统唯一确定地修正」**，而非「错误有多严重」。

| 类别 | 处理 | 例子 |
|---|---|---|
| **结构性非法** | **显式拒绝，抛错** | `outMs <= inMs`（源区间倒置）—— 没有合法解释 |
| **可自动修正的派生量** | **静默重算** | `durationMs` 与公式不符 —— 权威字段唯一确定答案 |
| **可自动修正的数值越界** | **静默钳制** | `scale` / `rotation` / `cornerRadius` / `lineHeight` —— 钳制到合法区间 |

**推论**：
- **不要为「系统已自动修好」的事打扰用户** —— 用户导入一个正常工程（可能来自旧版本或其他工具，数值略有偏差）却看到一堆警告，体验很差
- **但「系统无法确定怎么修」的事必须让用户知道** —— 静默接受非法数据会导致问题在管线深处以更难诊断的形式爆发
- **同一路径的行为必须与既有入口一致** —— `setClipProperty` 静默钳制，导入路径也应静默钳制

**已由本准则约束的决策**：FR-063（§9.10 决策一的三类分类表）、FR-064（静默钳制统一由公共约束函数承担）。

---

#### 准则三 · 同一约束在所有入口必须一致，且需有契约测试守护

本项目已实测出**三处**「约束只挂在部分入口」的缺口，且均为同一模式：

| 缺口 | 约束只挂在 | 漏掉的入口 | 后果 |
|---|---|---|---|
| fps 下限 | UI 下拉框选项 | Schema / 领域层 / 状态层 | 改一行 JSON 即绕过 |
| `durationMs` 不变式 | 编辑操作（`fixClipDuration`） | `deserialize` 导入路径 | 导入即产生违规数据 |
| `NUMERIC_RANGES` 12 条路径 | `setClipProperty` | `deserialize` 导入路径 | 11/12 字段在导入时完全失效 |

**推论**：
- **UI 层的限制不是约束** —— 下拉框选项、按钮禁用态都只约束「正常路径」，外部输入（粘贴、导入、JSON 编辑）可完全绕过
- **约束应下沉到领域层，并被所有入口共用** —— 这正是 FR-064 提升为 P0 的原因
- **跨字段的交叉约束必须显式断言** —— JSON Schema 表达不了 `durationMs == (outMs-inMs)/speed` 这类关系，只能靠领域层 + 契约测试
- **成对约束必须同时存在** —— D-001（片段 ≥100ms）与 D-003（fps ≥10）互为安全条件，缺一即失效

**已由本准则约束的决策**：FR-064（抽公共约束函数）、§9.12（双向契约断言）、D-003/D-001 的成对关系。

---

#### 准则四 · 静默即等于关闭警报

本项目已多次出现「静默处理掩盖了本该暴露的问题」：

- `deserialize` 静默接受不一致的 `durationMs` → 用户直到导出后才发现问题，且无从判断工程是否被改动
- 导出层静默丢弃不足一帧的片段 → 成片凭空少一段，零报错
- 切到「已完成任务」状态的需求 → 门禁核对时被视为已交付，**需求凭空消失**

**推论**：
- **静默只适用于「系统已确定性地修好」的情形**（准则二）
- **任何「用户可能因此损失内容或时间」的情形，必须显式告知**（准则一）
- **需求的状态与文档的存在性同等重要** —— 需求不可见 = 需求不存在

**已由本准则约束的决策**：D-003（不得静默钳制 fps，须告警）、FR-063（结构性非法须抛错）、§9.14（`check:prd-sync` 门禁脚本）。

| `assertClipInvariants` 含最小时长分支 | `invariants.ts:109-111` | 确有该分支，`< 100ms` 抛 `ClipInvariantError` |

| `fixClipDuration` 不做钳制 | `invariants.ts:88-91` | 钳制被刻意排除在 fix 之外，职责划分清晰 |

因此 QA 提出的「移除splitClip 校验会导致自产数据、自我断言报错」成立。**但这恰恰说明当前实现是正确的**——它把「不可分割」从事后抛错前移为入口显式拒绝。

#### 选A 的理由

1. **导出帧量化会导致静默丢帧（决定性理由）**
   片段时长若小于导出帧周期，编码器按帧取整后会输出 **0 帧**——用户时间线上看得到这个片段，成片里却凭空消失，且无任何报错。
   以 30fps 工程的 33ms 片段为例：导出 24fps 时 33/41.7 = 0.8 帧→ 归零。导出 30fps 时= 1 帧（勉强）。**同一个工程在不同导出帧率下行为不一致**，这类缺陷极难定位，会持续产生无法复现的 bug 报告。
   100ms 在任何 ≥10fps 的导出帧率下都 ≥1 帧，天然免疫该问题。

2. **专业软件的类比需要修正**
   需澄清一个常见误解：Premiere / 剪映**确实设限**，只是下限是「1 个项目帧」而非固定毫秒数。它们之所以能安全放开到帧级，是因为其**渲染管线全程帧锁定**（编辑期即以帧为单位存储与取样）。
   本项目的导出路径是 WebCodecs 离屏逐帧渲染，编辑期时间单位是毫秒、导出期才量化到帧，**不具备帧锁定的前提**。直接照搬帧级下限会引入上述静默丢帧风险。**架构不同，不能照搬竞品行为。**

3. **V1.0 阶段收益/成本比极差**
   放宽需同步修改 `assertClipInvariants` 最小时长分支 + `trimClip` / `addClip` / `setClipSpeed` 三个入口 + `minSourceSpanMs` 换算 + 全量测试与 QA 复验，且会连带引入 4 处下游二阶问题：预览采样闪烁、波形 400 采样点在超短片段上退化、撤销粒度异常、导出帧量化。
   而目标用户（US-01~US-05，3 分钟快速出片）几乎不会触发此边界。**这是典型的 power-user 特性，不属于 MVP 闭环。**

4. **一致性与可回滚性**
   100ms 已在 4 个操作入口统一生效且通过 QA 验证（BUG-01/06 均 FIXED）。放宽属不可逆决策，日后若发现真实用户强烈需要，须重新走一轮全量验证；收紧则随时可做。**MVP 阶段应选择可逆方向。**

#### 补齐项1：修正 FR-018① 表述（原表述不完整）

FR-018① 原文仅规定「距首尾 1 帧内不可分割」，**遗漏了最小时长约束**，导致实现超出文档字面要求。此为文档缺陷，现修正为**两级规则**：

> **FR-018①（修正）** 分割点须同时满足两级条件，任一不满足即拒绝并提示：
> - **T1 · 结构级**：分割点距 clip 首/尾均需 ≥ 1 帧（`1000 / canvas.fps` 毫秒）—— 防止产出零长度片段；
> - **T2 · 可用级**：分割后**两侧**时长均需 ≥ `MIN_CLIP_DURATION_MS`（100ms）—— 防止产出不可用碎片。
>
> 附加：两侧均满足时，视频 clip 分割后需生成第二段缩略图（原② 保留）。

同时 **FR-017②** 表述保持「最小 clip 时长 100ms」不变，与本规则对齐。

#### 补齐项 2：错误提示必须可操作（新增硬要求 P0）

当前 `NotSplittableError` 仅说明「被拒绝」，未告诉用户**怎么办**。用户拖动播放头误操作后会反复重试同一位置，体验上等同于「软件坏了」。

新增 **FR-018③（P0，编号已与 FR 表格对齐）**：

> 说明：本项是采纳方案 A 的**必要对价**。既然选择了「拒绝」，就必须让用户在被拒绝前就知道，而不是事后碰壁。
>
> **编号勘误**：本项最初写作 FR-018④，但 FR-018 原有②「视频 clip 分割后需生成第二段缩略图」在 FR 表格中顺延为 ③（本项），导致表格内不存在 ④。现统一为 **③**，§3.3 FR-018 行与本节一致。

#### 明确不做的事

- 极短片段（<100ms）在预览/导出的特殊处理：**本方案下不存在该问题**，因为此类数据无法被创建，无需设计丢弃或钳制逻辑。

### 9.4 D-003 · 导出帧率下限 10fps（新增P0 需求）

**触发**：QA 对 D-001 做安全前提验证时，发现 D-001 的论证存在未被保障的前提。

#### D-001 论证的自我修正

我在 D-001 中的论证是：

> 「100ms 在任何 **≥10fps** 的帧率下都 ≥1 帧，天然免疫该问题。」

**前半句（数学）成立，后半句（系统保障）在实现中并不存在。** 我当时只在 §9.3 写了一句"请确认 FR-038 的帧率可选值均 ≥10fps"作为**确认项**，这是我的判断失误——它把一个**尚不存在的能力**当成了**待确认的既有事实**。

#### QA 实测结论（已独立复核，全部属实）

| 层 | 位置 | 现状 |
|---|---|---|
| UI | `ExportSection.tsx:115` | ✅ 写死 `[24,25,30,50,60]` |
| Schema | `project.schema.json:80` / `:104` | ⚠️ `fps: {minimum: 1, maximum: 240}` —— **允许 fps=1** |
| 领域层 | `exportPlan.ts:74` | ⚠️ `Math.max(1, ...)` —— **有 `MAX_EXPORT_FPS=60`，无下限** |
| 状态层 | `operations.ts:931` | ⚠️ `setExportSettings` 无 fps钳制 |

**端到端绕过链（5 步，任何用户可复现）**：改工程 JSON 的 `"fps": 30` → `"fps": 5` → 导入成功无提示 → 导出无警告 → **时间线上可见的 100ms 片段在成片里凭空消失，零报错**。

**机制已定位**：`webCodecsExporter.ts:201` 按 `timeMs = index*1000/fps` 离散采样 + `compositor.ts:46` 用半开区间判定 —— 片段时长 < 帧周期且未跨越任何帧时刻，则整段一次都不被渲染。

**QA 全帧率扫描（100ms 片段 / 5000ms 工程）**：

| fps | 帧周期 | 采样结果 |
|---|---|---|
| 60/50/30/25/24 | 16.7~41.7ms | 2~6 帧 ✅ |
| **10** | 100.0ms | **1 帧← D-001 论证的下边界，成立** |
| 5 | 200.0ms | **0 帧 ❌** |
| 1 | 1000.0ms | **0 帧 ❌** |

该数据同时**验证了 D-001 的结论正确**（放宽到帧级确实会丢帧），并**暴露了 D-001 的前提缺乏防线**。

#### 决策

**接受 QA 提议，补充 FR-038②：工程文件中的 fps（`canvas.fps` 与 `export.fps`）不得低于 10。**

**为什么是 P0 而非 P1**：这不是"体验优化"，而是 **D-001 的正确性前提**。防线 A（片段 ≥100ms）单独存在并不足够—— 用户改一行 JSON 即可击穿。**两条防线必须同时存在**，否则 D-001 的结论在最常见的用户路径（导入他人分享的工程文件）上直接失效。

#### 关键设计约束（不可省略）

1. **不得静默钳制**：fps < 10 时**钳制到 10 并显式告警**，告知用户工程文件被调整。静默钳制会让用户困惑于"为什么我导出的帧率变了"。
2. **必须覆盖画布 fps，不只是导出 fps**：`canvas.fps` 决定预览与逐帧渲染的采样基准，`export.fps` 决定导出。两处都需收口，否则用户把 `canvas.fps` 设为 5 仍会在预览与导出中丢帧。
3. **契约测试形式化依赖关系**（采纳 QA 建议）：
   ```
   MIN_CLIP_DURATION_MS >= 1000 / MIN_EXPORT_FPS
   ```
   当前 `100 >= 1000/10 = 100` **恰好取等**。这条断言的意义不在于今天的数值，而在于**任一侧被改动时会立刻失败**，防止 D-001 的安全前提被无意破坏。建议作为单元测试固化。

#### 已升级为 V1.0 发布门禁

D-001 与 D-003 是**一组安全约束，不可拆分发布**。若仅发D-001 不发 D-003，则 100ms 限制可被一行 JSON 绕过，静默丢帧路径依然存在。

#### 决策一：新增 FR-063（P0，阻塞级）

**FR-063 · 导入路径必须执行 clip 级派生量重算与校验**

##### 三类数据处理方式的分类（实现不得有歧义）

「告警非阻断」这类笼统措辞会导致实现走偏。三类数据**必须区别对待**：

| 情形 | 处理方式 | 是否告知用户 | 理由 |
|---|---|---|---|
| **`outMs <= inMs`（源区间倒置）** | **显式拒绝，抛错，不让导入成功** | ✅ 必须告知（错误信息） | **结构性非法** —— 无法通过重算修正，倒置的源区间没有合法解释 |
| **`durationMs` 与公式不符** | **重算为正确值，不报错、不阻断导入** | ✅ **在导入路径告知**（见 FR-063⑦） | **派生量** —— 权威字段唯一确定答案，重算即可修正 |
| **其他数值字段越界**（`scale` / `rotation` / `cornerRadius` / `lineHeight` 等） | **静默钳制到合法区间** | ❌ **不告知** | 与 `setClipProperty` 既有行为一致，钳制属常规容错 |

**两个维度必须分开看**，这是本表最容易混淆之处：

```
处理方式  →  拒绝 / 重算 / 钳制     ← 决定「导入是否成功、数值是否被改」
是否告知  →  告知 / 不告知           ← 决定「用户是否需要知道」
```

**第三行「静默钳制且不告知」尤其重要**：否则用户导入一个正常工程（可能来自旧版本或其他工具、数值略有偏差）会看到一堆警告，体验很差。`setClipProperty` 当前就是静默钳制，**导入路径应保持一致**。

**第二行「重算且在导入路径告知」** 依据 FR-063⑦ —— 告警经返回值传递，**仅「用户主动导入外部工程文件」路径展示**；`loadProject` / `deleteProject` 不展示（那两条路径的数据由本应用自己写入，本就不该不一致）。

> **设计原则**：区分「结构性非法」与「可自动修正的数值偏差」—— 前者必须让用户知道并纠正，后者应静默处理避免噪音。**判断依据是「该错误能否由系统唯一确定地修正」，而非「错误有多严重」。**

##### 逐条要求（编号与 §3.10.1 FR-063 验收标准一一对应）

> **编号对应说明**：本表①~⑥ 与 §3.10.1 FR-063 验收标准①~⑤ **内容一一对应，但编号体系不同** —— 本表按「实现步骤」编号，FR 表格按「验收判据」编号。实现时请以**内容**为准，勿按编号机械对应。
>
> | 本表 | FR-063 验收标准 |
> |---|---|
> | ① 重算 | ① 重算生效 |
> | ② 数据地位 | ⑤ 派生/权威字段定义 |
> | ③ 重算不阻断 | ④ 不报错 |
> | ④ 文字 clip 例外 | ② 文字 clip 不被重算 |
> | ⑤ 源区间倒置拒绝 | ③ 显式拒绝 |
> | ⑥ 其他字段钳制 | — （由 FR-064 承担） |

| # | 要求 |
|---|---|
| ① | `deserialize` 对每个 `assetId !== null` 的 clip 调用 `fixClipDuration`，与现有 `meta.durationMs` 的处理方式**对称** |
| ② | **明确数据地位**：工程文件格式中 `durationMs` 为**派生字段**，`inMs`/`outMs`/`speed` 为**权威字段**。导入时**以权威字段重算派生字段** |
| ③ | `durationMs` 不符 → **重算并继续导入**（不抛错、不阻断）。**语义澄清：「重算」管「不阻断导入」，「告警」管「必须告知用户」，两者作用于不同环节，不构成矛盾** |
| ④ | **文字 clip 例外**：`assetId === null` 时直接返回原值，**不得**改为按公式重算（与 PRD「文字片段时长独立于素材」一致） |
| ⑤ | `outMs <= inMs` → **显式拒绝并抛错**（见上表第一行）—— JSON Schema 无法表达该交叉约束，只能在领域层判定 |
| ⑥ | 其他数值字段越界 → **静默钳制**（见上表第三行），由 FR-064 的公共约束函数统一承担 |
| ⑦ | **告警传递方式（落地约束，必读）** —— 见下方「FR-063⑦ 告警传递方式」 |

> **措辞修订说明**：本表初版③写作「静默重算，不报错、不告警」、⑥写作「静默钳制」。经 QA 复核指出，**「静默」一词被用于两个不同语义**（③ = 不阻断导入，⑥ = 不必告知用户），字面易生歧义。现已改为按环节分工的表述：**重算 → 不阻断导入（③）｜告警 → 必须告知用户（⑥的告警分支）｜拒绝 → 源区间倒置时抛错（⑤）**。

##### FR-063⑦ 告警传递方式（落地约束，必读）

**背景**：FR-063 要求「重算时必须告知用户」，但当前 `deserialize` 的签名是 `(json: unknown) => ProjectDoc` —— **返回值中没有任何通道能传递「发生了重算」这一信息**。若不指定通道，最自然的实现是「在 `deserialize` 内部直接 `toast()`」，而这会造成实际的用户骚扰。

**三个调用方对「要不要告警」的需求完全不同**（已实测确认调用点）：

| 调用方 | 场景 | 应否告警 |
|---|---|---|
| `ImportProjectDialog.tsx:59` | 用户主动**导入外部工程文件** | ✅ **应告警** |
| `projectRepo.ts:57` `loadProject` | 读取**本应用自己写入**的工程 | ❌ 不应告警 |
| `projectRepo.ts:75` `deleteProject` | 仅为提取 blobKey 而解析 | ❌ **绝对不应告警** |

**若在 `deserialize` 内直接 toast 的后果**：用户每次**删除工程**、每次**打开工程**都会莫名弹「工程文件存在不一致数据，已自动修正」。而正常 UI 操作产不出不一致数据 —— 这个提示**只会在异常场景出现**，恰恰是它的价值所在，**前提是它只在真正需要的场景出现**。

**决策（采纳 QA 方案 A）**：

| # | 要求 |
|---|---|
| ⑦-1 | 告警通过 `deserialize` 的**返回值**传递，`deserialize` **保持纯函数**（不碰 UI、不产生副作用、不 toast） |
| ⑦-2 | 由**调用方决定是否展示**；**仅「用户主动导入外部工程文件」路径需要展示** |
| ⑦-3 | 应用自身存储的工程读取路径（`loadProject`）与 `deleteProject` **不展示** |
| ⑦-4 | `deserializeFromJson` 与 `deserialize` 保持一致的返回结构 |

**建议的返回结构**（非强制，工程师可等价实现）：

```ts
export interface DeserializeResult {
  doc: ProjectDoc;
  warnings: DeserializeWarning[];   // 本次加载中被自动修正的不一致项
}
export interface DeserializeWarning {
  code: 'duration-recomputed' | 'value-clamped';
  clipId?: string; field?: string;
  expected: number; actual: number;
}
```

> **为什么不用回调参数（QA 备选方案 B）**：回调是**副作用**，容易在实现中滑向「随手传个 toast 进去」—— 而这正是骚扰问题的成因。返回值是数据，天然需要调用方显式消费，**在类型层面就杜绝了隐式 UI 行为**。
>
> **附带收益**：该结构让 QA 能直接断言「导入不一致工程 → `warnings.length > 0` 且 `warnings[0].code === 'duration-recomputed'`」，无需观察 UI 行为。

> ⚠️ **本节已修订**：早前版本要求「重算时显式告警」，与「静默钳制」并存会产生噪音（用户导入正常工程即见警告）。经复核，**`durationMs` 重算同样应静默**—— 用户无需感知系统替其修正了派生量。三类数据的最终处理方式以上表为准。

#### 决策二：新增 FR-064（**P0**，与 FR-063 同批交付）

**FR-064 · 导入路径应复用领域层数值范围约束**

要求把 `NUMERIC_RANGES` 抽为**可复用的领域层导出函数**，供 `setClipProperty` 与 `deserialize` 共用，消除「两条路径两套约束」的结构性隐患。

### 9.11 降级方向的方向性结论（更新，取代 §9.5 的对称表述）

QA 实测确认：**D-001 与 D-003 的依赖是单向的，不是对称不可分。**

| 组合 | 结果 | 理由 |
|---|---|---|
| 只有 **D-003**（fps ≥10） | ✅ **安全** | fps 恒 ≥10 时，任意长度片段都不会整段丢失 |
| 只有 **D-001**（片段 ≥100ms） | ❌ **不安全** | fps 可被设为 5 时，100ms 片段照样静默消失 |
| D-001 + D-003 | ✅ 安全 | 两条防线齐备 |

→ **修正 §9.5 的表述**：不是"不可拆分"，而是「**D-003 是 D-001 的前置安全条件**」。

#### 唯一的降级方向

| 方案 | 评价 |
|---|---|
| A：D-001 + D-003 一起发 | ✅ **推荐**（D-003 仅 4 处小改：Schema 2 行 + `exportPlan` 5 行 + `setExportSettings` 3 行 + 测试） |
| B：先发 D-001，D-003 延后 | ❌ **不安全** |
| C：D-001 降级为告警 | ❌ **最差**，见下 |
| D：**先发 D-003**，D-001 延后 | ✅ **唯一安全的降级方向** |

#### 为什么 C 是最差选项（QA 补充的硬理由，我采纳）

我原本的理由是「文档留白会被忽略」。QA 给出一条**更硬的**：

> **告警只在 UI 层，丢帧发生在导出层。**
> 在 D-003 实现前把 D-001 降级为告警，系统会**同时**做两件事：警告"此片段过短" + **静默丢掉它**。
> **告警拦不住已经在渲染管线中发生的丢帧** —— 等于把"明确拒绝"换成"警告 + 静默丢失"，用户体验**更差**（至少报错能让人知道发生了什么）。

**这与 FR-018③「必须前置预防、不能事后碰壁」是同一条产品原则**：能在入口拦住的问题，不要留到管线里静默失败。

### 9.12 契约测试：采纳 QA 的双向断言建议

我在 §9.4 提出单向断言 `MIN_CLIP_DURATION_MS >= 1000 / MIN_EXPORT_FPS`，QA 建议**补反向断言**。采纳：

```
MIN_CLIP_DURATION_MS >= 1000 / MIN_EXPORT_FPS   // 片段 ≥ 1 帧
MIN_EXPORT_FPS      >= 1000 / MIN_CLIP_DURATION_MS  // 帧周期 ≤ 最小片段时长
```

**两条合起来锁定「帧周期 ≤ 最小片段时长」这个双向关系，而非单向锁定。** 将来若有人调大 `MIN_CLIP_DURATION_MS` 或调小 `MIN_EXPORT_FPS`，两侧都会立刻失败。

> 当前数值下两条恰好都取等（100 == 1000/10 == 100）。**取等是预期状态**，须在测试旁加注释说明，避免后人误判为边界 bug 而"修正"它。

#### 判据 5 · 统计表漂移检测（采纳 QA 补充）

> 断言 PRD §3.11 统计表中的 P0 / P1 数量，与正文中实际标记为 P0 / P1 的 FR 条目数**一致**。

**理由**：§3.11 统计表是**手工维护**的（本项目已手工更新过 47→48、11→13、62→66）。手工维护的统计表天然会与正文漂移 —— 将来再加 FR 忘了更新 §3.11，就又是一次「描述偏差」。

这正是本项目两大风险源之一（描述偏差 / 状态错位），而**成本极低**：各 FR 行首列就是优先级标记，正则可数。

#### 判据 6 · 约束表单点挂载检测（采纳 QA 补充）

> 断言 `domain/` 下**不存在**「校验/钳制表仅被单一入口使用」的结构。

**实现思路（约 20 行静态检查）**：
1. 定位 `NUMERIC_RANGES`（或任何 `*_RANGES` / `*_LIMITS` 常量表）；
2. 统计其引用点；
3. 断言：引用点 **≥ 2**，且**必须包含 `domain/project/deserialize.ts`**（导入路径）。

**为什么这条能防复发**：本项目已实测的 4 项缺口（fps / `durationMs` / transform 范围 / canvas 尺寸）**根因完全相同** —— 约束表只挂在一个入口。将来有人又写一张新表只挂 UI 入口，判据 6 就会失败。

**它检查的是结构而非条目** —— 条目会随版本增删，结构不会。这条判据是 §9.0.1 准则三「同一约束在所有入口必须一致」的可执行形式。
