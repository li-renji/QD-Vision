### 教训：rebase 死循环（我自己定位的）
时钟 tick → setTimeMs → setCurrentTime → **clock.rebase()** → 锚点被重置 → 下一帧 delta≈0 → 时间停在第一帧。
「让 setCurrentTime 内部 rebase，时钟写回时锚点自动跟上」这个假设是错的 —— rebase 把**已推进的 delta 一起吃掉**。
修法：区分「外部写入」与「时钟写入」，后者不 rebase。

### 深层教训：测试通过 ≠ 功能正确（本次最重要的一条）
「有 clip 时 e2e 通过」掩盖了时钟推进其实是**靠 rAF 抖动攒出来的**，不是正确的。
根因是「自持基准（anchorTimeMs = nextMs）」与「无条件 rebase（anchorPerfMs = now()）」互相抵消：
- rebase 把 `anchorPerfMs` 重置为「现在」→ 每帧 delta ≈ 0 → 时间停在第一帧
- 有 clip 时 durationMs>0，微小 delta 累积仍能跨过帧边界 → e2e 断言侥幸通过
- 空工程 durationMs=0 → delta 完全为 0 → 1.5 秒后 currentTimeMs 仍是 16ms

**教训**：e2e 断言「时间码变了」太弱。正确断言应是
**「推进量 ≈ 真实经过时间（±20% 容差）」**，且必须覆盖 **durationMs=0 的边界场景**。
弱断言 + 单一场景 = 漏检。

## 【方法论：测「变速」必须用脉冲不能用正弦波】22:40
### 正弦波测频有假象
恒定速率输出 440Hz → 测得频率「保持 1.056」→ **看起来保音高成功了，其实根本没变速**。
「音高保持」与「时长压缩」是两个独立维度，正弦波只验证了前者。

### 脉冲法才能测出真相
输入 3s、每 0.5s 一个 20ms 脉冲，测输出脉冲间隔（真变速 → 间隔按 0.5/rate 变化）：
| rate | 脉冲数 | 平均间隔 | 期望 | 判定 |
|---|---|---|---|---|
| 1 | 6 | 0.500s | 0.500s | ✅ |
| 1.5 | **18** | 0.148s | 0.333s | ❌ 未变速且内容被撕裂复制 |
| 0.5 | 4 | 0.841s | 1.000s | ❌ |

**脉冲数从 6 变 18** → 不是变速，是内容被复制重排（算法在重叠区反复取同一段）。

### 教训（升级版）
上一条记的是「断言要验证推进量≈真实时间」，这条更具体：
- **验证「速率类」功能必须用「可数事件」而非「连续波形」** —— 脉冲/点击/帧号，间隔能直接反映速率
- 「输出时长 ≥ 800ms」这类断言**零信息量** —— 任何输出（含乱码）都满足
- 正弦波只适合验证「音高/频率」，不适合验证「时长/速率」

## 【变速链路最终方案】00:30 关键转折：preservesPitch 原生能力
### 结论
`playbackRate`（变速）+ `preservesPitch = true`（原生保音高）= 时长正确 + 音高不变，**全程不需要 worklet**。
PRD FR-020③ 早就写明「音频变速保持音高（preservesPitch=true）」—— **文档里已有答案，我们却去写了 400 行 WSOLA**。

### 实测（生产路径：元素 → createMediaElementSource → WebAudio，非裸元素）
```
rate=1.5 pp=true:   频率 445Hz  期望 440Hz  OK   ← 保音高生效
rate=1.5 pp=false:  频率 656Hz  期望 660Hz  OK   ← 对照组：不保音高确实变调
rate=0.5 pp=true:   频率 445Hz  期望 440Hz  OK
播放时长：rate=1.5 → 实播 4.08s（期望 4.00s）OK；rate=0.5 → 12.04s（期望 12.00）OK
```

### WSOLA 为什么失败（400 行作废的技术原因）
WSOLA 本质是**时间伸缩**（改时长），不能还原音高 —— 补偿音高需要 pitch shifter，是另一个算法。
且流式 AudioWorklet 的 `process()` 必须填满 128 样本块，无法同时满足「加速需更多素材 / 减速需攒素材」。
⇒ **用 Web 平台原生能力优先于自研算法**。

### 遗留限制（池化架构固有，非本轮引入）
同一素材被多个不同 speed 的 clip 复用时，音频无法同时满足多速率：
`previewFrameSource` 按 assetId 池化元素，一个元素同一时刻只能有一个 playbackRate。
画面侧靠「按 clip 计算 sourceTimeMs 再 seek 共享元素」规避，音频侧规避不了。

### 预览/导出不一致（平台限制，需告知用户）
- 预览：`element.preservesPitch` → 保音高
- 导出：`AudioBufferSourceNode` 无此属性 → 音高随变速变化（已用 warnings 告知）
